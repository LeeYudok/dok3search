# Codex 실전 가이드 2편 — 샌드박스와 승인 정책

Codex 실전 가이드 2편입니다. 1편에서 프로젝트 신뢰가 기본 샌드박스를 바꾼다는 이야기를 했습니다. 이번 편은 그 샌드박스와 승인 정책을 다룹니다. Claude Code 가이드에는 없는 주제입니다. Codex 에서 가장 먼저 부딪히는 차이가 여기 있어서 2편에 두었습니다.

이번 편이 답하는 질문은 이것입니다. **Codex 에게 어디까지 맡겨도 되고, 그 경계는 무엇이 지키나.** 답은 두 겹입니다. 운영체제 샌드박스가 파일 쓰기와 네트워크를 먼저 막습니다. 그다음 승인 정책과 rules 파일이 샌드박스 밖으로 나갈 명령을 고릅니다. 신뢰한 저장소의 기본값이면 저장소 안 편집은 맡겨도 됩니다. `.git` 쓰기, 네트워크, 저장소 밖 쓰기는 매번 사람에게 묻게 됩니다.

## 샌드박스는 세 단계이고 기본은 읽기 전용입니다

`codex --help` 의 `-s, --sandbox` 는 값 세 개를 받습니다. 공식 문서의 설명을 옮기면 이렇습니다.

| 값 | 공식 문서의 설명 |
|---|---|
| `read-only` | 파일을 볼 수는 있지만 승인 없이 편집하거나 명령을 실행하지 못한다 |
| `workspace-write` | 작업 폴더 안에서 읽고 편집하고 일상적인 로컬 명령을 실행한다 |
| `danger-full-access` | 샌드박스 제한 없이 실행한다 |

공식 문서의 설정 예시는 `sandbox_mode` 기본값을 `read-only` 로 적습니다. 1편에서 본 대로 제 맥에서는 신뢰한 저장소가 `workspace-write`, 처음 보는 폴더가 `read-only` 였습니다. 강제 수단은 운영체제 기능입니다. 공식 문서 기준으로 macOS 는 Seatbelt 정책과 `sandbox-exec` 를 씁니다. Linux 는 bwrap 과 seccomp 를 씁니다.

## workspace-write 도 .git 과 네트워크는 막습니다

신뢰한 저장소에서 `codex debug prompt-input` 을 보면 쓰기 가능한 경로가 셋 나옵니다. 저장소 폴더, `/private/tmp`, 그리고 사용자 임시 폴더(`$TMPDIR`)입니다. 같은 출력에 저장소 안이지만 읽기만 허용된 경로도 있습니다. `.git`, `.agents`, `.codex`, `.aws` 입니다. 공식 문서의 권한 설명도 이 네 경로를 읽기 전용으로 남긴다고 적습니다. 제 해석은 이렇습니다. 저장소 이력과 에이전트 자신의 스킬·설정을 에이전트가 고치지 못하게 막아 둔 듯합니다.

샌드박스 안에서 실제로 무엇이 막히는지는 `codex sandbox` 로 잴 수 있습니다. 이 명령은 Codex 가 쓰는 것과 같은 샌드박스 안에서 주어진 명령을 실행합니다. 빈 git 저장소에서 세 가지를 시도했습니다.

```bash
codex sandbox -- sh -c 'touch ok.txt; touch .git/probe; curl -s -m 5 https://example.com'
codex sandbox -c sandbox_mode="workspace-write" -- sh -c '...같은 명령...'
```

| 시도 | 기본(신뢰 안 한 폴더) | `workspace-write` |
|---|---|---|
| 작업 폴더에 파일 만들기 | 실패 | 성공 |
| `.git` 안에 파일 만들기 | 실패 | 실패 |
| 외부 주소로 HTTP 요청 | 실패(curl 종료 코드 6) | 실패(curl 종료 코드 6) |

`.git` 이 막혀 있으니 `git commit` 은 샌드박스 안에서 끝나지 않습니다. 커밋할 때마다 승인을 받거나, 다음 절의 rules 로 허용해야 합니다. 네트워크도 같습니다. 공식 문서는 `workspace-write` 의 네트워크가 기본으로 꺼져 있다고 설명합니다. 켜는 설정 키는 `sandbox_workspace_write.network_access` 입니다. 무엇이 막혔는지 모를 때는 `codex sandbox --log-denials` 를 씁니다. 도움말 기준으로 macOS 의 샌드박스 거부 기록을 모았다가 명령이 끝난 뒤 보여 줍니다.

## 샌드박스 밖으로 나가는 길은 승인과 rules 둘뿐입니다

prompt-input 의 권한 안내문에는 샌드박스 밖 실행 조건이 적혀 있습니다. 사용자가 승인했거나, 이미 있는 규칙이 그 명령을 허용했을 때입니다. 판정 단위도 정해져 있습니다. 명령줄을 파이프(`|`)·`&&`·`||`·`;`·서브셸 경계에서 조각으로 나누고, 조각마다 따로 판정합니다. 리디렉션, 치환, 환경변수 대입, 와일드카드가 든 명령은 규칙과 대조하지 않습니다.

모델이 승인을 요청하는 방식도 안내문에 있습니다. `sandbox_permissions` 에 `"require_escalated"` 를 넣고, `justification` 에 사용자에게 물을 질문을 적습니다. 원하면 `prefix_rule` 을 제안합니다. 사용자는 그 제안을 받아들여 다음 세션에도 쓸 규칙으로 남길 수 있습니다.

언제 물을지는 승인 정책(`approval_policy`, CLI 의 `-a`)이 정합니다. 0.169.0 의 `-a` 는 값 두 개만 받습니다.

- `on-request` — 모델이 판단해 승인을 요청합니다. 공식 문서의 설정 예시는 이 값을 기본값으로 적습니다.
- `never` — 묻지 않습니다. 실행이 실패하면 그 결과가 모델에게 바로 돌아갑니다.

공식 문서 기준으로 예전 값 `untrusted` 는 더 이상 지원하지 않고, `on-failure` 는 폐기 예정입니다. 예전 글에서 자주 보던 `--full-auto` 도 지원이 끝났습니다. 공식 문서는 대신 `--sandbox workspace-write` 를 쓰라고 안내합니다. 반대쪽 끝에는 `--dangerously-bypass-approvals-and-sandbox` 가 있습니다. 도움말은 이 옵션을 "외부에서 이미 격리된 환경 전용"이라고 적습니다.

그 사이에 `--approve-for-me` 가 있습니다. 승인 요청을 사람 대신 자동 검토로 보내고, 샌드박스는 `workspace-write` 를 씁니다. 자동 검토가 거절한 명령은 `/approve` 로 한 번 다시 시도할 수 있습니다(공식 문서 기준). 이 자동 검토가 어떤 기준으로 판정하는지는 확인하지 못했습니다. 세션 안에서 승인 없이 할 수 있는 범위를 바꾸는 명령은 `/permissions` 입니다(공식 문서 기준).

## rules 파일은 승인을 기억하는 곳입니다

한 번 승인한 명령을 다음에도 묻지 않게 하는 장소가 rules 파일입니다. 공식 문서 기준으로 위치는 설정 층 옆의 `rules/` 폴더(`~/.codex/rules/default.rules` 등)입니다. 저장소의 `.codex/rules/` 는 신뢰한 프로젝트에서만 읽습니다. 문법은 `prefix_rule()` 한 줄입니다.

```python
prefix_rule(pattern=["git", "push"], decision="allow")
prefix_rule(pattern=["git", "reset", "--hard"], decision="forbidden")
prefix_rule(pattern=["rm"], decision="prompt")
```

`decision` 은 `allow`·`prompt`·`forbidden` 셋입니다. 여러 규칙이 걸리면 `forbidden` > `prompt` > `allow` 순으로 가장 엄격한 쪽이 이깁니다. 공식 문서는 rules 를 아직 실험 기능이라고 적습니다. 규칙이 의도대로 걸리는지는 `codex execpolicy check` 로 확인합니다. 최상위 도움말 목록에는 없지만 0.169.0 에서 동작했습니다.

```bash
codex execpolicy check -r test.rules -- git reset --hard HEAD
# {"matchedRules":[...{"matchedPrefix":["git","reset","--hard"],"decision":"forbidden"}}],"decision":"forbidden"}
```

zsh 에서 명령을 변수에 담아 넘기면 단어로 쪼개지지 않습니다. 이때는 규칙이 하나도 걸리지 않은 결과가 나옵니다. 저도 처음에는 규칙이 고장 난 줄 알았습니다.

## Claude Code 와 다른 점 — 묻기 전에 먼저 막습니다

Claude Code 가이드 1편은 권한을 "처음엔 좁게, 쓰면서 넓히기"로 다뤘습니다. Codex 도 원칙은 같지만 첫 번째 방어선이 다릅니다.

| 항목 | Claude Code | Codex 0.169.0 |
|---|---|---|
| 첫 번째 방어선 | 도구를 쓰기 전에 묻는 권한 확인 | 운영체제 샌드박스 |
| 허용 기록 | 설정 파일의 허용·거부 목록 | `rules/*.rules` 의 `prefix_rule` |
| 판정 단위 | 도구와 명령 패턴 | 제어 연산자로 쪼갠 명령 조각 |

Claude Code 에서 허용 목록에 없는 명령은 사람에게 묻습니다. Codex 에서 샌드박스가 막는 명령은 묻기 전에 먼저 실패합니다. 그래서 승인 요청이 "무엇을 하려는가"보다 "왜 샌드박스 밖이어야 하는가"에 가깝습니다.

## 실사례 — 승인 버튼이 남긴 93개의 규칙

제 `~/.codex/rules/default.rules` 를 세어 보았습니다(2026-11-18). 규칙은 93개였고 전부 `allow` 였습니다. 그중 25개는 200자가 넘었고, 가장 긴 규칙은 5,938자였습니다. 열어 보니 이슈 본문 전체를 인자로 넣은 이슈 생성 명령이 통째로 규칙이 되어 있었습니다. 한 번만 쓸 명령을 "다음에도 허용"으로 승인한 결과입니다. 이런 규칙은 같은 명령이 다시 올 일이 없으니 아무것도 허용하지 못합니다.

비용은 다른 곳에서 나옵니다. 승인한 규칙은 매 세션 권한 안내문의 "Approved command prefixes" 목록으로 들어갑니다. 신뢰한 저장소에서 잰 권한 안내문은 9,270자였습니다. 끝에는 "[Some commands were truncated]" 가 붙어 있었습니다. 승인 한 번이 이후 모든 세션의 컨텍스트를 조금씩 차지하는 셈입니다.

반대 방향의 위험도 있습니다. 목록에 `["curl"]` 이 `allow` 로 들어 있었습니다. 안내문의 규칙대로라면 `curl` 로 시작하는 명령 조각은 샌드박스 밖에서 실행됩니다. 네트워크를 막아 둔 샌드박스가 curl 에 한해서는 꺼진 것과 같습니다. 안내문도 `["python3"]` 처럼 넓은 접두어는 제안하지 말라고 모델에게 지시합니다. 사람 쪽에서도 같은 기준으로 승인해야 합니다.

지금은 두 가지를 지킵니다. 승인할 때는 `["git", "push"]` 처럼 짧고 범주가 분명한 접두어만 남깁니다. 그리고 rules 파일을 가끔 열어 200자가 넘는 규칙과 너무 넓은 접두어를 지웁니다.

## 정리

Codex 의 경계는 두 겹입니다. 샌드박스가 쓰기와 네트워크를 먼저 막습니다. 승인 정책과 rules 가 샌드박스 밖으로 나갈 명령을 고릅니다. 신뢰한 저장소의 기본값이면 저장소 안 편집은 맡겨도 됩니다. 커밋과 네트워크는 승인이나 규칙이 있어야 하고, 그 규칙은 짧은 접두어로만 남깁니다.

다음에 확인할 것은 하나입니다. `~/.codex/rules/` 를 열어 `curl`·`python3` 처럼 넓은 `allow` 규칙이 있는지 보는 것입니다. 3편에서는 `config.toml`·프로필, 그리고 세션을 열자마자 차 있는 컨텍스트를 다룹니다.
