# 세 사람과 에이전트가 한 main 을 쓰면 생기는 일 — git 사고 세 건과 막는 장치

> 세 사람과 에이전트 여럿이 브랜치 없이 main 하나에 바로 커밋하면 무엇이 깨질까?

답부터 적는다. 코드보다 이력이 먼저 깨진다. 35일 동안 세 건이 났다. 원격 main 이 내용은 같고 해시만 다른 이력으로 바뀌었다. LFS 체크아웃에 실패한 자리에서 커밋해 파일 853개가 삭제로 기록됐다. 저자 이름은 9종으로 흩어졌다. 세 건 모두 규칙은 문서에 있었고, 막는 장치는 없었다.
대상은 은행 개발 조직의 3인 팀이 쓰는 레포다. 비공개 레포라 본문의 커밋 해시는 독자가 열어 볼 수 없다. 기록을 위해 남긴다. 수치는 2026-11-18 에 `git log` 와 `git show --stat` 으로 다시 셌다.

> [그림] 왼쪽에는 끝이 끊긴 짧은 원격 철길과 더 길게 이어진 로컬 철길이 나란히 있고, 크레인 로봇이 -s ours 라고 적힌 연결 선로를 내려 둘을 잇는다. 오른쪽에는 체크아웃 상자가 넘어져 파일이 쏟아지고, 삭제 853건 표지판 옆에서 pre-commit 로봇이 멈춤 판을 든다

그림으로 줄이면 이렇다. 왼쪽은 공통 조상 없는 두 이력을 연결 선로로 잇는 장면이다. 오른쪽은 쏟아지는 파일 옆에서 커밋 직전 검사가 멈춤 판을 드는 장면이다.

사람은 셋이고, 에이전트는 Claude Code·Codex·Antigravity 를 섞어 쓴다. 기능 브랜치나 병합 요청 없이 각자 main 에 커밋하고 푸시한다. 레포에는 커밋과 푸시를 대신 하는 git 동기화 스킬도 있다. 이 스킬은 `git add -A`, 커밋, 푸시를 차례로 실행한다. 푸시 전에 원격을 받아 오는 단계는 없다.

## 원격 main 이 서명만 빠진 다른 이력으로 바뀌었다

2026-11-17 에 한 PC 에서 원격을 받아 보니 공통 조상이 없었다. 원격 main 은 22커밋짜리 이력이었다. 그날 만든 병합 커밋(0f615ef)의 메시지는 이를 "강제 푸시로 갈라진 원격 이력"이라고 적는다.

그 메시지가 적은 판단 근거는 둘이다. 원격 끝 커밋의 트리가 로컬 466dd8a(2026-10-15 09:06:59)의 트리와 같다. 원격 22커밋의 제목이 모두 로컬 이력에 있다. 로컬에는 466dd8a 뒤로 325커밋이 더 있었다.

2026-11-18 에 한 걸음 더 들어갔다. 원격 22커밋과 로컬 앞 22커밋을 순서대로 짝지어 커밋 객체를 비교했다.

| 항목 | 원격 | 로컬 앞부분 |
|---|---|---|
| 커밋 수 | 22 | 22 |
| 끝 커밋의 트리 | `e2c150f` | `e2c150f` |
| 짝마다 트리·저자·커미터·시각·메시지 | 22짝 모두 같다 | 22짝 모두 같다 |
| GPG 서명이 붙은 커밋 | 0 | 8 |
| 첫 커밋 해시 | `366b80e` | `89e81e3` |

차이는 서명 하나였다. 로컬의 첫 커밋에는 서명이 있었다. 서명이 빠지면 첫 커밋의 해시가 바뀌고, 부모 해시를 품는 뒤 커밋 21개도 줄줄이 바뀐다. 내용은 그대로인데 git 은 남남인 두 이력으로 본다.

누가, 왜, 어떤 도구로 서명을 뺀 이력을 올렸는지는 레포에 적혀 있지 않아 확인하지 못했다. 이력을 다시 쓰는 도구는 대개 원래 서명을 남기지 않는다. 그래서 다시 쓰는 과정에서 빠졌다고 추정한다.

## 상위 집합임을 확인하고 이력만 이었다

길은 셋이었다. 원격으로 되돌리면 로컬 325커밋을 잃는다. 325커밋을 원격 위로 다시 쌓으면(rebase) 다른 PC 들도 가진 커밋의 해시가 모두 바뀐다. 그 PC 들이 같은 일을 다시 겪는다. 남은 길이 `-s ours` 병합이다. 파일은 로컬 그대로 두고 원격 이력을 부모로만 붙인다.

```bash
git merge-base main origin/main || echo "공통 조상 없음"          # 1. 갈라졌는가
t=$(git rev-parse 'origin/main^{tree}')
git log --format='%H %T' main | awk -v t="$t" '$2==t {print $1}'  # 2. 같은 트리의 로컬 커밋
comm -23 <(git log --format=%s origin/main | sort) \
         <(git log --format=%s main | sort)                    # 3. 로컬에 없는 원격 제목
git rev-list --count <2의 커밋>..main                           # 4. 로컬에만 있는 커밋 수
git merge -s ours --allow-unrelated-histories origin/main       # 5. 이력만 잇는다
```

이 순서는 2026-11-18 에 연습 레포로 다시 돌려 보았다. 병합 뒤 트리는 병합 전 로컬과 같았다. 원격 끝이 로컬 이력의 조상이 되어 푸시는 빨리 감기(fast-forward)로 끝났다.

두 가지를 조심한다. 첫째, 3번의 제목 비교는 약한 증거다. 병합 전 로컬 이력에는 두 번 이상 나오는 제목이 3개 있었다. 확실히 하려면 위 표처럼 짝지은 커밋의 트리와 메시지를 비교한다. 둘째, `-s ours` 는 원격에만 있는 변경을 소리 없이 버린다. 원격이 로컬의 부분집합이라는 확인 없이 쓰면 남의 작업을 지운다.

같은 날 22:38 에 로컬 60커밋을 더 가진 다른 PC 가 이 병합을 받아 합쳤다(bbd8b69). 결과 트리는 그 PC 의 로컬 트리와 같았다. 이력만 이은 병합이라 파일 변화가 번지지 않았다.

## LFS 체크아웃이 실패한 자리에서 커밋하면 전부 삭제로 기록된다

2026-10-26 15:00:02 의 커밋(c53e0dd)은 새 폴더 하나를 더하려던 커밋이었다. 기록은 달랐다. 파일 34개를 더하고 853개를 지웠다. 줄 수로는 3,269줄 추가, 162,040줄 삭제다. 바로 앞 커밋의 파일이 853개였으니 레포 전체를 지운 셈이다. 공통 지침 파일과 작업자 확인 훅 스크립트도 지운 목록에 있었다.

22초 뒤 커밋(641e1cd)이 853개를 모두 되살렸다. 메시지는 "LFS 체크아웃 실패 상태에서 커밋되어 853개 파일이 삭제로 기록"됐다고 적는다. 되살린 트리를 사고 직전과 비교하면 새로 더한 34개 말고는 차이가 없다. 두 커밋 모두 에이전트 공동 저자 표시가 붙어 있다.

LFS 체크아웃이 왜 실패했는지는 레포에 적혀 있지 않아 확인하지 못했다. 실패가 전부 삭제로 이어지는 과정은 연습 레포로 재현했다(2026-11-18, git-lfs 3.8.0). LFS 파일 하나와 문서 5개가 든 레포를 만들고, 원격의 LFS 객체를 지운 뒤 clone 했다.

```text
warning: Clone succeeded, but checkout failed.
$ git status --short
D  .gitattributes
D  docs/d1.md
  ... (모두 7개)
D  install/a.bin
```

clone 은 성공했다고 하지만 인덱스(스테이징 영역)는 비어 있다. 그래서 파일 7개가 모두 '삭제 예정'으로 잡힌다. 이 상태에서 새 파일 하나만 `git add` 하고 커밋하니 기록은 `8 files changed, 1 insertion(+), 9 deletions(-)` 이었다. 경고 한 줄을 놓치면 다음 커밋이 레포를 지운다.

두 커밋은 12분 뒤 다른 PC 의 병합(1f690ce)으로 공유 이력에 들어갔다. 그때 원격 끝은 이미 되살린 커밋이었다. 원격 끝이 지운 커밋이던 순간에 누가 받아 갔는지는 확인하지 못했다. 흔적은 숨는다. 기본 `git log -- .gitattributes` 는 이 두 커밋을 보여 주지 않는다. 병합 한쪽 갈래에만 있고 결과가 다른 쪽과 같아 git 이 그 갈래를 생략한다. `--full-history` 를 줘야 보인다.

막는 장치는 커밋 직전 검사다. 스테이징된 삭제 수가 기준을 넘으면 멈춘다.

```sh
#!/bin/sh
# pre-commit: 스테이징된 삭제가 기준을 넘으면 커밋을 멈춘다
max=${MAX_DELETES:-50}
n=$(git diff --cached --diff-filter=D --name-only | wc -l | tr -d ' ')
if [ "$n" -gt "$max" ]; then
  echo "pre-commit: 삭제 ${n}건 (기준 ${max}건). 의도했으면 MAX_DELETES=${n} 로 다시 커밋한다." >&2
  exit 1
fi
```

연습 레포에서 기준을 3으로 두니 "삭제 7건"에서 커밋이 멈췄다. 훅 파일은 git 이 나눠 주지 않는다. 레포의 `scripts/` 같은 곳에 두고, PC 마다 `git config core.hooksPath` 로 가리키게 한다. 에이전트가 쓰는 커밋 절차에도 같은 검사를 넣는다. 지금의 git 동기화 스킬은 바뀐 파일 목록을 출력만 하고 삭제 수는 세지 않는다.

## 저자 이름 9종과 병합 11건이 이력을 흐린다

세 번째는 쌓인 결과다. 사람은 셋인데 저자 이름은 9종, 메일은 10종, 이름과 메일 조합은 11종이다. 메일을 둘씩 쓰는 이름이 2개, 이름 둘이 나눠 쓰는 메일이 1개다. 에이전트 계정 이름이 하나(37커밋), '알 수 없음'을 뜻하는 자리표시 이름이 하나(23커밋)다. 이 둘을 빼도 이름은 7종이다.

그러면 `git shortlog -sn` 이 사람 셋에 9줄을 낸다. 에이전트 커밋을 남기는 방식도 섞였다. 에이전트 계정이 저자인 커밋이 37개, 공동 저자 표시가 붙은 커밋이 32개다. 둘 다인 커밋도 10개다. 해석은 이렇다. 커밋한 곳마다 저자 설정이 달랐고, 그것을 맞추는 장치가 레포에 없다. 작업자 전환 스크립트는 git 저자 설정을 보여 주기만 하고 바꾸지는 않는다. 한 사람이 일부러 여러 이름을 쓴 것이라면 이 해석은 틀린다. 그 의도는 확인하지 못했다.

병합 11건도 같은 뿌리에서 나왔다. 모두 원격 main 을 로컬 main 에 합쳤다. 0f615ef 를 뺀 10건 가운데 양쪽이 1커밋씩 갈라진 것이 3건이다. 한쪽이 18커밋 이상 앞선 것이 4건이고, 가장 크게는 로컬 60 대 원격 23 이었다. 병합 자체는 해롭지 않다. 다만 누가 언제 무엇을 합쳤는지 읽기 어려워진다. 앞의 삭제 커밋이 기본 `git log` 에서 숨은 것도 이 구조 때문이었다.

흩어진 이름은 `.mailmap` 으로 묶는다. 이미 남은 커밋을 고치지 않고 `shortlog` 와 `log` 의 표시만 사람 단위로 바로잡는다.

```text
# .mailmap: <정식 이름> <정식 메일> <커밋에 남은 이름> <커밋에 남은 메일>
작업자A <a@example.com> 다른이름 <old-a@example.com>
```

앞으로는 작업자를 바꿀 때 저자 설정도 함께 맞춘다. 에이전트 커밋을 남기는 방식도 하나로 정한다. 에이전트 계정을 저자로 쓰거나, 사람을 저자로 두고 에이전트를 공동 저자로 적는다.

## 세 사고 모두 규칙은 문서에 있었고 장치는 없었다

팀의 git 규칙 문서에는 main 강제 푸시 금지, 원자적 커밋, `.gitattributes` 로 줄바꿈 맞추기 같은 항목이 있다. 실제 `.gitattributes` 는 LFS 규칙 두 줄뿐이고 줄바꿈 설정은 없다.

| 사고 | 문서에 있던 규칙 | 레포에서 찾은 장치 | 더할 장치 |
|---|---|---|---|
| 서명 빠진 원격 이력 | main 강제 푸시 금지 | 찾지 못했다. 서버 설정은 확인하지 못했다 | 서버의 main 보호(강제 푸시 거부) |
| 853개 삭제 커밋 | 원자적 커밋 | 없다. 동기화 스킬은 `git add -A` 뒤 바로 커밋한다 | 커밋 직전 삭제 수 검사 |
| 저자 9종, 병합 11건 | 없다 | 없다 | `.mailmap`, 전환 때 저자 고정, 푸시 전 원격 받기 |

문서 규칙은 부탁이다. 꼭 지켜야 하는 것은 훅과 서버 설정이 막게 한다.

## 이 판단이 틀리는 경우

- 기능 브랜치와 병합 요청을 쓰는 팀이면 첫째와 셋째 사고는 브랜치 보호와 리뷰에서 대부분 걸린다. 이 글의 처방은 main 에 바로 커밋하는 팀에 맞춘 것이다.
- 삭제 수 기준값은 레포마다 다르다. 정리 커밋은 일부러 많이 지운다. 멈추고 사람이 보게 하는 것이 목적이다.
- 서명 빠진 이력이 왜 올라왔는지 모른다. 원인이 강제 푸시가 아니라 레포를 새로 만든 일이었다면 막는 장치도 달라진다.

## 정리

세 사람과 에이전트가 main 하나를 쓰면 코드보다 이력이 먼저 깨진다. 깨진 자리는 모두 문서 규칙만 있고 장치가 없던 곳이었다.

다음에 확인할 것은 하나다. 지금 쓰는 서버에서 main 에 강제 푸시를 시도하면 거부되는가.
