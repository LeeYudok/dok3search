# 2026년 웹 프론트엔드 기술스택 2탄 — 빼라던 것은 빠졌고, 온다던 것은 오지 않았다

> 1탄에서 "검토해볼 만하다"고 적은 것들은 여덟 달 뒤 내 package.json 에 실제로 들어왔을까?

답부터 적습니다. 빼라고 한 것은 빠졌고, 새로 오리라던 것은 대부분 오지 않았습니다. Axios 는 새 프로젝트에서 사라졌고 서버 상태는 TanStack Query 가 맡았습니다. RSC, TanStack Start, Bun 패키지 관리는 쓰지 않았고, React Compiler 는 한 곳에서만 켰습니다.
1탄의 예측 열 가지 가운데 다섯이 맞았습니다. 근거는 2026-11-18 에 다시 읽은 프로젝트 다섯 개의 `package.json` 입니다.

> [그림] 왼쪽 책상에 문서 검색, 분석 데모, 공유기 콘솔, 관리 콘솔, 증시 포털의 package.json 다섯 장이 놓여 있다. 로봇이 빨간 펜으로 오른쪽 1탄 채점표에 맞음, 한 곳, 빗나감, 뒤집힘을 매긴다

그림으로 줄이면 이렇습니다. 지금 손대는 `package.json` 다섯 장을 펴 놓고 1탄의 문장을 하나씩 대 봤습니다. 맞힌 것은 "빼도 된다" 쪽이었고, 빗나간 것은 "새것이 온다" 쪽이었습니다.

[1탄](https://blog.doksam.com/blog/web-tech-stack-2026/)은 2026년 3월에 프로젝트 하나의 `package.json` 을 열어 "이 정도면 최신인가"를 따진 글입니다. 7월에 한 번 고쳤고 끝에 9점을 줬습니다. 이 글의 버전은 각 `package.json` 에 적힌 값이고, "최신" 칸은 같은 날 `npm view <패키지> version` 으로 읽은 값입니다. 프로젝트 이름은 하는 일로 바꿔 적었습니다.

## 1탄의 예측 열 가지 가운데 다섯이 맞았습니다

| 1탄에서 한 말 | 2026-11-18 의 다섯 프로젝트 | 판정 |
|---|---|---|
| Axios 대신 `fetch` 나 ky | 다섯 모두 Axios 도 ky 도 없다 | 맞음 |
| Recharts 는 잘 돌면 유지 | 차트가 있는 두 곳이 Recharts 3.10.1 | 맞음 |
| 서버 상태는 TanStack Query, 커지면 Zustand | Query 넷, Zustand 하나 | 맞음 |
| 라우터는 React Router 나 TanStack Router | React Router 넷, TanStack Router 하나 | 맞음 |
| 성능이 중요한 도구는 Rust 로 바뀐다 | Vite 8 넷, oxlint 하나 | 맞음 |
| React Compiler 는 이제 켜고 쓸 때 | 증시 포털 한 곳만 켰다 | 한 곳 |
| ESLint·Prettier 대신 Biome 적극 검토 | 화면 쪽은 oxlint 하나, 나머지는 린터가 없다 | 빗나감 |
| RSC 가 확산된다 | 다섯 모두 SPA 다 | 빗나감 |
| TanStack Start 가 대항마다 | 쓴 곳이 없다 | 빗나감 |
| Bun 이 확산된다 | 다섯 모두 `packageManager` 가 pnpm | 뒤집힘 |

"성능이 중요한 도구는 Rust 로" 판정의 근거는 Vite 8 입니다. 2026-03-12 의 [Vite 8 발표](https://vite.dev/blog/announcing-vite8)에 따르면 Vite 8 의 번들러는 Rolldown 하나입니다. 발표문은 Rolldown 을 "Rust-based bundler" 라고 적습니다.

### Axios 는 새 프로젝트에서 사라졌습니다

요청은 전부 `fetch` 로 보냅니다. 재시도, 캐시, 로딩 상태는 TanStack Query 가 다루니 `fetch` 를 감싼 함수 하나면 됩니다. 1탄에서 대안으로 적은 ky 도 쓰지 않았습니다. Axios 가 남은 곳은 7월 이후 손대지 않은 1탄 프로젝트와 같은 뼈대의 저장소뿐입니다.

### 상태 관리는 서버 상태부터 들어왔습니다

1탄은 Zustand 를 먼저 적고 TanStack Query 를 다음에 적었습니다. 실제 순서는 반대였습니다. 화면이 가진 상태의 대부분은 서버에서 온 데이터였습니다. 그것을 Query 로 옮기고 나니 전역으로 들고 있을 것이 거의 남지 않았습니다.

### RSC 는 쓰지 않았고, 이 사이트는 오히려 걷어 냈습니다

다섯 프로젝트 어디에도 화면을 서버에서 그릴 Node 프로세스가 없습니다. 컨테이너 파일을 확인한 세 곳은 `node:22` 단계에서 화면을 빌드하고 결과물만 다음 단계로 옮깁니다. API 는 셋 다 Go 서버가 맡습니다. 이 구조에서 RSC 를 넣으면 서버 바이너리와 정적 파일 폴더로 끝나는 배포가 사라집니다.

이 사이트도 같은 길을 갔습니다. 2026-11-17 까지 Next.js 16 의 App Router 로 돌다가 Hugo 와 작은 Go 서버로 바꿨습니다. 다섯 프로젝트의 `src/` 를 검색해 보니 React 19 의 `use()`, `useActionState`, `useOptimistic` 을 쓴 파일은 하나도 없었습니다.

### 린트는 Biome 이 아니라 oxlint, 아니면 tsc 뿐입니다

막상 필요했던 것은 린트뿐이었고, 그래서 더 작은 oxlint 를 골랐습니다. 분석 데모의 스크립트는 `"lint": "oxlint"` 한 줄입니다. 나머지 넷은 `build` 가 `tsc --noEmit && vite build` 처럼 타입 검사부터 돌리고, 테스트가 있는 곳은 Vitest 나 Playwright 가 동작을 봅니다.

Biome 이 없는 것은 아닙니다. 다섯 프로젝트 밖의 서버·도구 쪽 `package.json` 여섯 곳에 Biome 2.4 가 있습니다. 1탄의 예측은 화면 쪽에서 빗나갔고 서버 쪽에서는 맞았습니다.

### React Compiler 는 한 곳에서 켰습니다

증시 포털의 `vite.config.ts` 는 `@vitejs/plugin-react` 의 `reactCompilerPreset()` 으로 `babel-plugin-react-compiler` 1.0.0 을 켭니다. 1.0.0 은 2026-11-18 의 최신 판이기도 합니다. 켜기 전후로 렌더 횟수가 얼마나 줄었는지는 재지 않았습니다.

### Bun 에서 pnpm 으로 옮긴 이유는 배포였습니다

1탄은 "이미 Bun 을 쓰고 있다"로 끝났습니다. 지금은 다섯 프로젝트 모두 `packageManager` 칸에 pnpm 이 적혀 있습니다. 바꾼 이유는 속도가 아니라 배포였습니다.

- 빌드는 컨테이너 안에서 끝나고, 배포 서버에는 Node 도 Bun 도 깔지 않습니다.
- 의존성 취약점을 점검하고 버전을 올리는 절차를 pnpm 기준으로 만들어 두었습니다. 도구가 둘이면 절차도 두 벌이 됩니다.
- CI 는 `pnpm install --frozen-lockfile` 로 락파일과 다르면 실패하게 둡니다.

Bun 이 없어진 것은 아닙니다. 작은 도구와 일부 서버는 지금도 Bun 으로 돌립니다.

## 버전은 프로젝트마다 만든 날의 최신에서 멈춥니다

위 표에서 TypeScript 는 5.7, 5.9, 6.0, 7.0 이 한꺼번에 나옵니다. Vite 는 6 과 8 이 같이 있습니다. 모두 2026년에 손댄 프로젝트입니다.

처음 올린 2탄은 "3월에 최신이던 Vite 7"이라고 적었습니다. 다시 확인하니 틀린 문장입니다. npm 기록으로 Vite 8.0.0 은 2026-03-12 에 나왔습니다. 1탄은 그 아흐레 뒤에 Vite 7 을 "최신"으로 적었습니다. "최신 버전 사용 중"이라는 칭찬은 쓰는 순간 이미 한 판 뒤였습니다.

해석은 이렇습니다. 프로젝트는 만든 날의 최신에서 멈추고, 그 뒤로는 올릴 이유가 생길 때만 올립니다. 문서 검색이 Vite 6 에 있는 것은 잘 돌고 있어서입니다. 이 해석은 보안 패치가 나오면 틀립니다. 1탄이 적은 2025년 12월의 RSC 취약점처럼 고칠 이유가 생기면 만든 날과 상관없이 올려야 합니다.

## 겪은 함정은 빌드와 배포의 경계에 있었습니다

프런트엔드 작업 지침에 2026-09-09 부터 적어 둔 내용입니다.

| 함정 | 증상 | 대처 |
|---|---|---|
| pnpm 과 서버의 Node | pnpm 11 은 Node 22.13 이상이 필요하다(`npm view pnpm@11.9.0 engines`). Node 20 대 서버에서 `ERR_UNKNOWN_BUILTIN_MODULE` 로 죽었다 | `packageManager` 와 서버의 pnpm 을 같은 판으로 고정 |
| 인증 예외 경로 | `/static/` 을 로그인 검사에서 빼 두고 빌드 결과를 통째로 올리면 `index.html` 도 로그인 없이 열린다 | `assets/` 만 예외 경로에 두고 `index.html` 은 로그인이 걸린 주소에서 내보낸다. Vite 의 `base` 를 그 경로에 맞춘다 |
| `key` 없는 재사용 | 같은 컴포넌트를 다른 데이터로 다시 그리면 앞 화면의 입력값이 남는다 | 데이터가 바뀌는 자리에 `key` 를 준다 |
| 백엔드만 보는 CI | 프런트 빌드가 깨져도 CI 가 초록색이다 | 검증 단계에 프런트 설치와 빌드를 넣는다 |
| 빌드를 잊음 | 고쳤는데 화면이 그대로다 | 로컬 실행 스크립트가 `src/` 가 `dist/` 보다 새로우면 스스로 빌드한다 |

```bash
pnpm --dir web install --frozen-lockfile
pnpm --dir web build
```

## 다시 매긴 총평

1탄은 9점을 줬습니다. 지금 보면 그 점수는 "버전 숫자가 높은가"를 잰 것입니다. 여덟 달 동안 실제로 값을 한 기준은 달랐습니다.

| 1탄의 기준 | 지금의 기준 |
|---|---|
| 버전이 최신인가 | 올릴 이유가 생겼을 때 올릴 수 있는가 |
| 유행하는 라이브러리를 골랐는가 | 의존성이 몇 개인가 |
| 새 기능을 쓸 수 있는가 | 배포물이 얼마나 단순한가 |
| 빠진 도구는 없는가 | 없어도 되는 도구는 없는가 |

이 판단이 틀리는 경우도 있습니다.

- 다섯 프로젝트는 모두 Go 서버 뒤에 붙인 화면입니다. 화면을 서버에서 그리는 Node 팀이라면 RSC 와 TanStack Start 의 판정은 다를 것입니다.
- 표본이 다섯이고, 판정은 `package.json` 에 무엇이 있는지만 봤습니다. 코드에서 얼마나 쓰는지는 재지 않았습니다.

## 정리

1탄의 마지막 문장은 "최신이냐보다 프로젝트에 맞느냐가 중요하다"였습니다. 여덟 달 뒤의 `package.json` 은 그 문장대로 됐습니다. 빼도 되는 것은 빠졌고, 새것은 이유가 생긴 한 곳에만 들어왔습니다.

다음에 볼 것은 하나입니다. 증시 포털에서 React Compiler 를 켜기 전후로 렌더 횟수가 실제로 줄었는지 재 보겠습니다.
