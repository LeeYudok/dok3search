# Go 와 Rust 를 쓰면 좋은 점 — 직접 잰 숫자로 본 두 언어의 자리

> 코드는 에이전트가 쓴다. 그러면 언어는 아무거나 골라도 되지 않을까?

답부터 적는다. 오히려 언어를 더 가려야 한다. 에이전트는 빨리 쓰고 자주 틀린다. 틀린 것을 배포 전에 잡아 주는 컴파일러와, 파일 하나로 끝나는 배포가 그 속도를 받아 낸다.
그래서 평소 일은 Go 로 하고, Go 로 안 되는 곳만 Rust 로 한다. 아래는 그렇게 정한 근거다. 숫자는 2026-11-18 에 내 저장소에서 직접 쟀다.

> [그림] 왼쪽은 상자 하나를 들고 달리는 배달 로봇 Go, 오른쪽은 돋보기로 부품을 검사하는 검수 로봇 Rust. 가운데 시계 아래에 고치고 다시 빌드하는 시간 0.3초와 40초가 적혀 있다

그림으로 줄이면 이렇다. Go 는 상자 하나를 들고 빨리 달리는 배달부다. Rust 는 오래 들여다보고 틀린 것은 통과시키지 않는 검수원이다.

## 먼저 잰 숫자부터 본다

대상은 둘이다. Go 쪽은 이 사이트의 서버다. 정적 파일을 내보내고 문의 접수만 처리한다. Rust 쪽은 문서 변환 엔진이다. HWP·PDF·DOCX 같은 문서를 Markdown 으로 바꾼다.

| 항목 | Go (이 사이트 서버) | Rust (문서 변환 엔진) |
|---|---:|---:|
| 코드 | 481줄 (테스트 207줄) | 50,472줄 |
| 외부 의존성 | 직접 1개, 간접 5개 | 잠금 파일 기준 420개 |
| 처음부터 빌드 | 4.1초 | 86초 |
| 한 파일 고치고 다시 빌드 | 0.3초 | 40.8초 |
| 테스트 한 번 | 1.5초 | 재지 않았다 |
| 실행 파일 | 15.8MB | 6.8MB |

두 프로젝트는 크기가 100배쯤 다르다. Rust 쪽은 링크 시점 최적화(LTO)까지 켠 릴리스 빌드다. 그래서 이 표는 언어끼리의 공정한 시합이 아니다. 내가 두 언어로 일할 때 실제로 기다리는 시간이다.
측정 환경은 Apple M4 Pro 14코어, Go 1.26.2, rustc 1.100.0 이다. Go 는 빌드 캐시를 비우고 쟀고, Rust 는 빈 폴더에 새로 빌드했다.

## Go 는 배포가 파일 하나로 끝난다

**Go 로 만든 서버는 실행 파일 하나다.** 이 사이트의 컨테이너에는 그 파일과 정적 파일만 들어 있다. 셸도 패키지 관리자도 없는 이미지(distroless static)에서 돈다. 런타임을 따로 깔 일이 없다.

**다른 운영체제용 빌드는 명령 한 줄이다.** 맥에서 환경 변수 두 개(`GOOS`, `GOARCH`)를 바꿔 리눅스용과 윈도우용을 만들었다. 크기는 각각 16.1MB, 16.3MB 였다. 교차 컴파일러를 따로 설치하지 않았다.

이 성질이 가장 쓸모 있던 곳은 폐쇄망이다. 한국어 글 검사기는 윈도우·리눅스·맥용 실행 파일 세 개를 릴리스에 올린다. 폐쇄망 PC 에는 그 파일 하나만 들고 들어가면 된다. 설치할 것이 없다.

## Go 는 표준 라이브러리만으로 일이 된다

**증시 차트 도구는 외부 의존성이 0개다.** Go 1,284줄이다. HTTP 요청, JSON 처리, 파일 다루기, 테스트가 모두 표준 라이브러리에 있다. 차트는 SVG 문자열을 직접 만든다.

의존성이 없으면 지킬 것도 없다. 취약점 알림이 오지 않고, 내려받을 패키지가 없으니 폐쇄망에서도 그대로 빌드된다. 에이전트가 이름이 비슷한 엉뚱한 패키지를 끌어올 일도 없다.

이 사이트 서버도 직접 의존하는 것은 PostgreSQL 드라이버 하나다. 나머지 다섯은 그 드라이버가 데려온 것이다.

## Go 는 고치고 확인하는 주기가 초 단위다

**한 파일을 고치고 다시 빌드하는 데 0.3초, 테스트까지 1.5초다.** 사람에게는 그냥 빠른 것이지만 에이전트에게는 일하는 방식이 달라진다. 에이전트는 고칠 때마다 형식 검사, 정적 검사, 테스트를 돌린다. 이 주기가 2초면 한 작업에서 수십 번 돌려도 부담이 없다.

**형식이 하나뿐인 것도 크다.** `gofmt` 가 정한 모양 말고는 없다. 에이전트 셋이 번갈아 고쳐도 줄 바꿈과 들여쓰기로 diff 가 더러워지지 않는다.

반대 사례가 어젯밤에 있었다. 원고를 변환하려고 급히 쓴 Python 스크립트가 실행 도중 타입 오류로 죽었다. 문자열을 받는 함수에 목록을 넘겼기 때문이다. Go 였다면 빌드에서 걸렸을 실수다. 그 스크립트는 지금 Go 로 옮길 목록에 있다.

## 작은 도구를 Rust 로 짰다가 Go 로 되돌렸다

**위에서 말한 글 검사기는 사실 Rust 로 먼저 옮겼다.** 원래는 Python 스크립트였다. Rust 판은 그날 안에 접었다. 2026-11-13 의 일이다.

문제는 실행 속도가 아니라 빌드였다. 검사기는 소스가 바뀌면 처음 실행할 때 스스로 빌드한다. Rust 판은 그때마다 정규식 패키지를 포함한 릴리스 빌드를 돌렸다. 그동안 CPU 를 오래 붙잡았고, 빌드 산출물이 캐시에 146MB 쌓였다.

Go 표준 라이브러리만 쓰는 판으로 다시 짜니 빈 캐시에서도 첫 빌드가 약 2초에 끝났다. 내려받을 패키지가 없어 네트워크도 필요 없다. 기존 사례 64개의 검사 결과는 그대로였다.

값은 치렀다. Go 의 정규식에는 전후방 탐색이 없다. 금지 표현 표가 쓰던 앞뒤 경계 조건을 엔진이 따로 처리하도록 손봐야 했다. 그래도 바꿀 만했다. 글 한 편 검사하는 도구에 필요한 것은 최고 속도가 아니라 바로 뜨는 것이었다.

## Rust 는 Go 로 안 되는 곳에서 쓴다

**문서 변환 엔진은 남이 만든 파일을 뜯는 일이다.** HWP, PDF, 오래된 오피스 형식을 바이트 단위로 읽는다. 형식이 깨진 파일과 일부러 망가뜨린 파일이 들어온다. 여기서는 속도와 메모리 안전이 같이 필요하다.

**이 엔진의 소스 5만 줄에는 `unsafe` 가 한 줄도 없다.** 메모리를 잘못 건드리는 종류의 버그는 컴파일러가 막아 준다는 뜻이다. 파서가 이상한 입력을 받고 죽을 수는 있어도, 엉뚱한 메모리를 읽어 넘기지는 않는다.

**실행 파일은 6.8MB 하나다.** 가비지 컬렉터도 런타임도 없다. 저장소 README 에는 9개 형식 1,000개 파일을 20ms 에 처리한다고 적혀 있다. 이 수치는 이번에 다시 재지 않았다.

재다가 알게 된 것도 있다. README 에는 실행 파일이 2.4MB 라고 적혀 있었다. 새로 빌드해 보니 6.8MB 였다. 형식을 늘리는 동안 문서의 숫자가 낡았다. 수치는 날짜와 함께 적어야 한다는 것을 다시 배웠다.

## Rust 는 한 번 짠 코어를 여러 곳에 붙인다

**같은 엔진이 다섯 가지 모양으로 나간다.** 명령줄 도구, Rust 라이브러리, Python 모듈, Node 모듈, MCP 서버다. 변환 로직은 하나이고 겉만 다르다. Python 을 쓰는 데이터 작업과 에이전트가 부르는 도구가 같은 결과를 낸다.

Go 로도 다른 언어에 붙일 수는 있다. 다만 런타임과 가비지 컬렉터가 따라가서 남의 프로세스 안에 넣기가 번거롭다. 다른 언어에 끼워 넣을 코어는 Rust 가 맞다.

## Rust 의 값은 기다리는 시간이다

**처음부터 빌드하는 데 86초, 한 파일을 고치면 40.8초가 걸렸다.** 의존 패키지 215개를 컴파일했고 잠금 파일에는 420개가 있다. Go 의 0.3초와 견주면 고치고 확인하는 주기가 100배 넘게 길다.

이 시간은 에이전트에게도 그대로 든다. 고칠 때마다 40초를 기다리면 한 작업에서 돌릴 수 있는 확인 횟수가 준다. 그래서 Rust 작업은 한 번에 크게 고치지 않고, 테스트를 좁혀 돌리게 한다.

대신 빌드를 통과한 코드는 믿을 만하다. 소유권과 수명 규칙이 에이전트가 자주 내는 실수를 막는다. 공유 데이터를 동시에 고치는 코드나 해제한 값을 다시 쓰는 코드는 빌드가 되지 않는다.

## 그래서 이렇게 고른다

| 상황 | 고르는 것 | 이유 |
|---|---|---|
| API 서버, 배치, 명령줄 도구 | Go | 빨리 고치고 파일 하나로 배포한다 |
| 폐쇄망에 들고 갈 도구 | Go | 의존성 없이 실행 파일 하나 |
| 남이 만든 파일을 뜯는 파서 | Rust | 속도와 메모리 안전이 함께 필요하다 |
| 여러 언어에서 불러 쓸 코어 | Rust | 런타임 없이 끼워 넣는다 |
| 화면 | TypeScript | 브라우저가 정한다 |
| 서버 설치와 배포 절차 | 셸 | 명령을 잇는 일이다 |

내 저장소 90개 가운데 Go 를 쓰는 곳은 17개이고, 그중 10개는 Go 가 주 언어다(2026-08-16 집계). Rust 로 크게 짠 것은 문서 변환 엔진 하나다. 비율이 곧 판단이다. 대부분의 일은 Go 로 충분하다.

## 이 판단이 틀리는 경우

- 팀에 Go 나 Rust 를 읽을 사람이 없으면 틀린다. 에이전트가 쓴 코드를 검토할 사람이 있어야 한다.
- 데이터 분석과 모델 학습은 Python 이 맞다. 라이브러리가 거기에 있다.
- 며칠 쓰고 버릴 스크립트는 어떤 언어든 상관없다. 다만 내 경험으로는 버린다던 스크립트가 반년을 산다.
- Rust 빌드가 지금보다 훨씬 빨라지면 Go 를 고를 이유가 줄어든다.

## 정리

에이전트가 코드를 쓰는 지금, 언어를 고르는 기준은 사람이 쓰기 편한가에서 틀린 것을 얼마나 일찍 잡는가로 옮겨 갔다. Go 는 그 확인을 2초 안에 끝내고 파일 하나로 배포한다. Rust 는 더 많이 잡는 대신 40초를 받는다.

평소 일은 Go 로 한다. 속도와 안전이 함께 걸린 곳만 Rust 로 한다. 다음에 새 서비스를 시작할 때는 먼저 물어볼 것이 하나다. 이 일이 Go 로 안 되는 이유가 있는가.
