# 윈도우에서는 WSL2, AI 개발은 맥 아니면 리눅스 — 도구는 돌아도 생태계는 리눅스다

> AI 코딩 에이전트는 이제 윈도우에서도 설치된다. 그러면 윈도우에서 그냥 쓰면 되지 않을까?

답부터 적는다. 도구는 뜨지만 일은 리눅스 말로 한다. 에이전트가 치는 명령, 훅, 설치 스크립트, 모델 서빙이 모두 리눅스를 전제로 한다.
그래서 윈도우 PC 라면 WSL2 안에서 쓰고, 새로 장비를 고른다면 맥이나 리눅스를 고른다. 아래는 문서로 확인한 것과 직접 겪은 것이다. 확인한 날은 2026-11-18 이다.

> [그림] 윈도우 섬과 리눅스 섬 사이에 WSL2 다리가 놓여 있고, 에이전트 로봇이 다리를 건너 리눅스 섬의 터미널·컨테이너·GPU 서버로 간다. 맥은 아래에서 리눅스에 바로 접속한다

그림으로 줄이면 이렇다. 에이전트가 쓸 도구는 리눅스 섬에 있다. 윈도우에서는 WSL2 라는 다리를 건너야 하고, 맥은 같은 말을 써서 바로 닿는다.

## 도구는 윈도우에서도 뜬다

먼저 오해부터 걷는다. "윈도우에서는 안 된다"는 옛말이다. 공식 문서 기준으로 두 도구 모두 윈도우에서 바로 실행된다.

| 도구 | 윈도우 그대로 | WSL2 |
|---|---|---|
| Claude Code | 설치된다. Git for Windows 가 있으면 Bash 도구를, 없으면 PowerShell 도구를 쓴다. 샌드박스는 지원하지 않는다 | 설치된다. 샌드박스를 지원한다 |
| Codex | PowerShell 에서 윈도우 샌드박스로 실행된다 | 리눅스 도구가 필요하거나 작업이 이미 WSL2 에 있을 때 쓰라고 안내한다 |

Claude Code 문서는 고르는 기준을 한 줄로 적는다. 윈도우용 프로젝트와 도구라면 윈도우 그대로, 리눅스 도구 모음이나 샌드박스가 필요하면 WSL2 다.

문제는 AI 개발에서 쓰는 도구가 거의 다 뒤쪽이라는 점이다.

## 에이전트가 치는 명령이 리눅스 말이다

**에이전트는 셸 명령으로 일한다.** 파일을 찾고, 테스트를 돌리고, 커밋한다. 그 명령은 대부분 bash 문법이다. 프로젝트에 넣어 둔 훅과 배포 스크립트도 셸 스크립트다.

내 설치 스크립트가 그 증거다. 개발 환경을 한 번에 깔아 주는 스크립트는 윈도우의 Git Bash 에서 실행하면 첫 단계에서 멈춘다. 안내문은 이렇다. WSL2 를 설치하고 그 안에서 실행하라.
멈추게 만든 이유가 있다. Git Bash 에는 zsh 와 패키지 관리자가 없다. 그래서 셸 설정, 플러그인, 설치 되돌리기가 성립하지 않는다. 흉내 낸 리눅스로는 끝까지 가지 못했다.

WSL2 안에서는 같은 스크립트가 리눅스 경로를 그대로 탄다. 윈도우용 분기를 따로 만들 일이 없다.

## 한글이 깨진다 — 직접 겪은 세 가지

윈도우에서 가장 많이 시간을 쓴 곳은 기능이 아니라 글자였다.

1. **PowerShell 5.1 은 BOM 없는 스크립트를 cp949 로 읽는다.** 한글 주석이 든 `.ps1` 파일이 구문 오류로 죽었다. 그래서 내 저장소의 `.ps1` 은 UTF-8 BOM 과 CRLF 로, `.cmd` 는 ASCII 로만 쓴다는 규칙을 두었다.
2. **윈도우의 Python 은 하위 프로세스의 출력을 CP949 로 읽는다.** 글 검사기의 Python 호환 계층이 Go 엔진이 낸 UTF-8 JSON 을 읽지 못했다. 인코딩을 `utf-8` 로 못박아 고쳤다(2026-11-17).
3. **PowerShell 5 의 파이프는 한글을 바꿔 보낼 수 있다.** 그래서 검사기 사용 안내에는 표준 입력 대신 파일 경로를 주라고 적었다. 출력이 깨지지 않게 `chcp 65001` 을 먼저 치라는 줄도 있다.

셋 다 리눅스와 맥에서는 생기지 않는 일이다. 거기서는 처음부터 UTF-8 이다. 지금은 CI 에 윈도우 실기 검사를 넣어 두었다. 그 검사를 만들다가도 한글 리터럴 때문에 한 번 더 고쳤다.

줄바꿈도 같다. 저장소 기본은 LF 이고 윈도우 스크립트만 CRLF 다. 이 구분을 `.gitattributes` 에 적어 두지 않으면 에이전트가 고친 파일의 모든 줄이 바뀐 것으로 잡힌다.

## 심볼릭 링크와 샌드박스가 다르다

**심볼릭 링크가 기본으로 되지 않는다.** 내 스킬 저장소는 원본 하나를 세 에이전트의 폴더에 링크로 건다. 윈도우에서는 링크를 만들지 못해 복사본으로 떨어지고 경고가 나온다. 복사본이 원본과 어긋나지 않게 커밋 전에 막는 검사를 따로 넣어야 했다.

**샌드박스도 다르다.** Claude Code 는 윈도우 그대로에서는 샌드박스를 지원하지 않고 WSL2 에서는 지원한다(공식 문서 기준). 에이전트에게 명령 실행을 넓게 맡길수록 샌드박스가 중요해진다. 윈도우 그대로 쓰면 그 안전장치 하나가 빠진다.

## 모델을 직접 돌리면 리눅스다

**내 GPU 서버는 리눅스다.** 24GB 그래픽 카드 두 장으로 오픈소스 모델을 서빙한다. 서빙 엔진, 컨테이너, 쿠버네티스가 모두 리눅스 위에 있다. 배포는 루트 권한 없는 컨테이너로 한다.

윈도우에서 같은 것을 하려면 결국 WSL2 나 가상 머신 안에 리눅스를 올린다. 그럴 바에는 처음부터 리눅스가 낫다.

## 쿠버네티스도 리눅스 위에 선다

**쿠버네티스(k8s)의 노드는 리눅스다.** 컨테이너가 리눅스 커널의 기능으로 만들어지기 때문이다. 맥이나 윈도우에서 쿠버네티스를 띄우는 도구들은 안에 리눅스 가상 머신을 하나 둔다. GPU 를 컨테이너에 넘기는 장치 플러그인과 런타임도 리눅스용이다.

내 GPU 서버가 그 예다. 노드 하나짜리 클러스터에서 모델 서빙 파드가 그래픽 카드 두 장을 쓴다. 인그레스 14개와 인증서 9개도 같은 클러스터가 맡는다(2026-11-15 실측).

처음에는 k3s 로 시작했다. k3s 는 쿠버네티스를 실행 파일 하나로 묶은 가벼운 배포판이다. 123일 동안 썼고, 2026-11-15 에 kubeadm 으로 설치한 정식 쿠버네티스 v1.37.2 로 바꿨다. 둘의 차이는 무엇이 딸려 오느냐다.

| | k3s | kubeadm 쿠버네티스 |
|---|---|---|
| 설치 | 실행 파일 하나 | 패키지와 컨테이너 런타임을 따로 깐다 |
| 인그레스·DNS·저장소·지표 | 기본으로 들어 있다 | 하나씩 골라 설치한다 |
| 네트워크(CNI) | 내장 | 직접 고른다. 나는 flannel 을 썼다 |
| 맞는 곳 | 혼자 쓰는 서버, 빠른 시작 | 표준 구성과 같게 맞추고 싶을 때 |

옮길 때는 파드와 서비스의 주소 대역, 인그레스 이름, 인증서를 그대로 가져갔다. 그래서 배포 스크립트는 고치지 않았다. 스크립트가 k3s 전용 명령 없이 `kubectl` 만 썼던 덕이다.

배운 것이 하나 더 있다. 2026-08-02 에 클러스터가 통째로 멈춘 적이 있다. 원인은 방화벽이었다. 파드 대역을 허용하는 규칙이 빠져 있었다. 쿠버네티스를 굴리려면 리눅스의 네트워크와 방화벽을 알아야 한다. 이 지식은 윈도우에서 쌓이지 않는다.

맥에서는 클러스터를 띄우지 않는다. 설정 파일 하나로 리눅스 서버의 클러스터에 `kubectl` 을 붙여 쓴다.

**맥은 손에 드는 쪽이다.** 에이전트 세 개와 브라우저 자동화, 예약 실행을 맥에서 돌린다. 터미널과 셸이 리눅스 서버와 거의 같아서, 맥에서 짠 스크립트가 서버에서 그대로 돈다. 작은 모델은 맥에서 바로 띄워 시험한다.

정리하면 손에 드는 장비는 맥, 모델이 사는 곳은 리눅스다. 윈도우는 이 둘 사이에 다리(WSL2)를 놓아야 한다.

## WSL2 를 쓸 수 없는 곳도 있다

폐쇄망이 그렇다. 인터넷이 안 되고 WSL2 를 켤 수 없는 윈도우 PC 가 있다. 여기서는 차선책을 쓴다.

- Git for Windows 설치 파일을 반입해 오프라인으로 설치하는 스크립트를 따로 두었다. Git Bash 용 설정만 깔고, 리눅스 전용 기능은 넣지 않는다.
- 도구는 실행 파일 하나로 만든다. 글 검사기는 윈도우용 실행 파일을 릴리스에 올려 두었다. 설치할 것이 없으니 반입 목록이 짧다.
- 스크립트의 인코딩과 줄바꿈 규칙을 시험으로 고정한다. 실제 설치는 윈도우에서만 확인할 수 있어서, 맥에서는 인코딩·줄바꿈·문법까지만 검사한다.

돌아가기는 한다. 다만 기능이 줄고, 손이 더 간다.

## 그래서 이렇게 고른다

| 상황 | 고르는 것 | 이유 |
|---|---|---|
| 윈도우 PC 로 AI 개발 | WSL2 안에서 | 셸·스크립트·샌드박스가 리눅스 기준이다 |
| 새 개발 장비 | 맥 | 서버와 같은 셸, 에이전트 여러 개를 띄우기 편하다 |
| 모델 서빙·GPU | 리눅스 | 서빙 엔진과 컨테이너가 리눅스에 있다 |
| 쿠버네티스 | 리눅스. 혼자면 k3s, 표준에 맞추려면 kubeadm | 노드가 리눅스다 |
| 폐쇄망 윈도우 | Git Bash 와 실행 파일 하나짜리 도구 | WSL2 를 켤 수 없다 |
| 윈도우용 프로그램 개발 | 윈도우 그대로 | 빌드 도구가 윈도우에 있다 |

WSL2 를 쓸 때 지킬 것은 둘이다. 에이전트는 WSL 터미널 안에서 설치하고 실행한다. 글꼴은 윈도우 쪽에 깐다. 화면을 그리는 것은 윈도우의 터미널이기 때문이다.

## 이 판단이 틀리는 경우

- 만드는 것이 윈도우용 프로그램이면 틀린다. .NET, 게임, 윈도우 드라이버는 윈도우 그대로가 맞다.
- 회사 정책으로 WSL2 를 켤 수 없으면 선택지가 없다. 위의 차선책으로 간다.
- 도구의 윈도우 지원은 계속 좋아진다. Codex 는 이미 윈도우 샌드박스를 갖췄다. 샌드박스와 셸 차이가 사라지면 이 글의 절반은 낡는다.

## 정리

도구가 윈도우에서 설치되는 것과 윈도우에서 일이 되는 것은 다르다. 에이전트가 치는 명령, 스크립트, 인코딩, 모델 서빙은 아직 리눅스를 기준으로 짜여 있다.

윈도우에서는 WSL2 안에서 쓴다. 장비를 고를 수 있으면 손에는 맥을, 서버에는 리눅스를 둔다. 윈도우 그대로 버틸 때 드는 비용은 기능이 아니라 깨진 글자와 예외 처리에서 나온다.
